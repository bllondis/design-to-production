<Section label="The problem" title="A portfolio about parity can't be built on copied values">
  This site argues that design and code should mean the same thing. Hand-copied hex values, pixel sizes and one-off
  hover colours would quietly contradict that. I wanted every visual decision to have one name, one source, and an
  automatic way to check that it is still used correctly.
</Section>

<Principle text="A design decision has one name and one source, wherever it is used." />

<Section label="System architecture" title="One pipeline from token to page">
  Tokens are written once, in the W3C design tokens format. A build step turns them into CSS for the components and a
  JSON list for documentation. Figma holds the same tokens as variables, so a designer and the code are pointing at the
  same decision.
</Section>

<Note label="Boundary">
  The app imports the system only through its package names. The packages never import from the app, so the system could
  ship to a second product without changes.
</Note>

<Section label="Tokens" title="Three tiers, each with one job">
  Primitives hold raw values and mean nothing on their own. Semantic tokens say what a value is for: a surface, a line,
  muted text. Component tokens hold the decisions that belong to one component, such as a button's hover fill, and point
  at semantic ones. Components never reach past that to a primitive.
</Section>

<Note>
  The generated CSS keeps references (`outputReferences`), so the alias chain stays readable in the browser's inspector:
  a component token resolves through its semantic role to the primitive.
</Note>

<Section label="Figma" title="The same names in Figma, with code attached">
  Figma has three variable collections that match the three tiers one to one. Every variable carries its CSS name as
  code syntax, so Dev Mode shows `var(--button-light-bg)` rather than a hex value. Semantic and Component have two
  modes, Desktop 1440 and Mobile 375, so a designer sees the sizes the site actually renders at each width.
</Section>

  that are easy to forget, such as reduced motion and accessible names, are part of the component rather than a
  checklist next to it.
</Section>

<Section label="Where it got complicated" title="Three problems worth keeping">
  Most of the system was straightforward to build. These three needed a second look, and each changed how the system
  works.
</Section>

<Cards columns={3}>
  <Card title="Transparency disappeared in the build">
    Translucent borders were written as `rgb(… / a)`. Style Dictionary's colour transform dropped the alpha, so every
    grid line turned solid. **Rewriting the primitives as `rgba()`** kept the source readable and the output correct.
  </Card>
  <Card title="Fluid sizes on a fixed canvas">
    The site's type and spacing use `clamp()`, which Figma can't express. I resolved each value at 1440 and 375 and
    stored them as **two variable modes**, so switching the mode shows the real sizes rather than a guess.
  </Card>
  <Card title="An arrow Figma couldn't colour">
    The ↗ in buttons isn't in Urbanist. Figma drew it with a fallback font that ignored the fill, so the arrow vanished
    on light buttons. **Setting the glyph in Inter** let it take its colour and size from the component tokens.
  </Card>
</Cards>

<Section label="Working with AI" title="Rules an AI agent can follow">
  I build with AI coding agents, so the system's rules live in the repository, in a file agents read before they change
  anything. The same rules a reviewer would enforce are written down once: which tokens to use, where new components go,
  and which checks must pass.
</Section>

<Note>
  The guardrails are mechanical where they can be: lint and type errors, failing tests and changed screenshots stop a
  change. The written rules cover what a tool can't judge, such as choosing the right semantic role.
</Note>

</Section>

<Section label="Reflection" title="What this work reinforced" />

<Cards columns={2}>
  <Card title="Names are the real interface">
    Hex values change; names last. Most of the work was choosing names that mean the same thing to a designer in Figma,
    a developer in CSS and an agent reading the rules.
  </Card>
  <Card title="Tooling is part of the design">
    A decision that can't be checked will drift. Tests, screenshots and CI are how a design system keeps its promises
    after the first release.
  </Card>
